# 設計案：まちとバスを選んで登録する（2026-11-24、まだ作っていません）

## したいこと

- 最初の画面で、都道府県 → バスの名前を選ぶ。そのバスの停留所から、移動を登録する。
- 改正のデータがまだ無いバスも選べるようにし、「いまのところ、時刻が変わる知らせはありません」と出す。
- そのために、現行の版の時刻表を、端末で読める形にして配る。

## データの持ち方

GitHub Pages（site ブランチ）に、次の3種類を置きます。

| ファイル | 中身 | いつ作り直すか |
|---|---|---|
| `data/catalog.json` | 都道府県 → バスの一覧。バスごとに名前・事業者・ライセンス・時刻表のファイル・改正のデータの一覧・時刻表を作った日 | 見に行くたび |
| `data/timetables/{org}__{feed}.json` | **時刻表のデータ**（現行の版と、出ていれば「次」の版） | そのフィードに新しい版が出たとき |
| `data/revisions/{org}__{feed}/{変更日}__{uid}.json` | 改正のデータ（いまと同じ） | 便や時刻が変わる版が出たとき |

### 時刻表のデータの形

日ごとに書き出す改正のデータとは違い、**運行の決まりをそのまま持ち、その日に走るかを端末で計算します。** 日がたっても作り直さなくてよいので、版が変わったときだけ作り直せば済みます。

```
{
  "meta": { "feed", "feed_name", "operator", "license", "license_url", "attribution", "built_at" },
  "versions": [                                   // 現行と「次」。有効期間で、その日に使う版を選ぶ
    { "uid", "published_at", "from", "to",
      "stops":    [[名前, 読み, 緯度, 経度], ...],
      "routes":   [路線名, ...],
      "services": [{ "wd": "1111100", "s": "20261201", "e": "20270331", "add": [...], "rm": [...] }, ...],
      "trips":    [[路線, 行き先, 運行の番号, [[停留所, 時刻] か [停留所, 着, 発], ...]], ...] }
  ]
}
```

- 祝日・年末年始・一日だけの特別な日の決まりは、改正のデータと同じものを、端末の側で計算します（`calendar_rules.py` と同じ決まりを `judge.js` にも持たせます。祝日の一覧は `catalog.json` に入れます）。
- 停留所の対応・のりばの移動・いちばん近いバス停などは、いまの判定の部品をそのまま使えます。

### アプリの流れ

1. 都道府県を選ぶ（`catalog.json` だけを読む。gzip で約15KB）
2. バスを選ぶ → そのバスの時刻表のデータを読む
3. 乗るバス停・降りるバス停・曜日・時刻（いまの登録と同じ）
4. 一覧：
   - そのバスに、これから先の改正のデータがあれば、いまと同じように知らせを出す
   - 無ければ「いまのところ、時刻が変わる知らせはありません」と、時刻表のデータから「いまのバス」を出す
5. 1つのバスに改正のデータが2つ以上あるとき（例：本荘地区の 12/01 と 3/23）は、日付の順に知らせを出します。

## 大きさの見積もり

測ったもの：手元に現行の版の zip がある78フィードで、試しに時刻表のデータを作りました。

| | 大きさ（gzip） |
|---|---|
| 試した78フィードの中央 | 13KB |
| 試した中の最大（長崎県営バス 3,826便） | 217KB |
| 新常磐交通（1,536便。zip は 8.5MB だが、ほとんどが路線の形） | 178KB |

全国の見積もり：全612フィードの現行の版の zip の大きさを調べ（先頭1バイトだけ取る方法。2件は取れず）、上の比（時刻表の gzip ÷ zip）を当てはめました。

| | 合計（gzip） |
|---|---|
| 公開できる608フィード（CC BY 4.0、CC0 1.0、CC BY 2.1 JP）の zip の合計 | 87MB |
| 時刻表のデータの合計（比の 25%〜75%） | **約5〜18MB**（中央 約9MB） |
| 1フィードの中央 | 約3.5KB |
| 9割のフィード | 30KB 以下 |
| `catalog.json` | 約90KB（gzip 約15KB） |

- 使う人が読むのは、`catalog.json` と、選んだバスの時刻表と改正のデータだけです。ふつうは合わせて数十KB、大きいバスでも数百KBです。
- GitHub Pages のサイトの大きさの上限（1GB）にも、十分に収まります。
- 比で見積もると、路線の形が大きいフィードでは大きく出すぎます（新常磐交通は比では848KB、実際は178KB）。そのため、合計は上の見積もりより小さくなるはずです。

## 作るときの手間と、見る仕組みへの影響

- **最初に1回**：608フィードの現行の版（と「次」の版）の zip を落として作ります。87MB、およそ20分です。週1回の点検の時間に作るか、手元で作って site ブランチに入れます。
- **そのあと**：新しい版が出たフィードだけ作り直します。毎日更新の12フィードは、指紋が変わった日だけ作り直します（指紋が同じなら、便と時刻は同じため）。
- 「次」の版の有効開始日が来たときは、作り直さなくても、端末が日付で版を選びます。
- 掛川市の2フィード（ライセンスの「CC-BY」のバージョンが分からない）は、一覧には出しますが、時刻表のデータは配りません。「このバスの時刻表は、いまは使えません」と出します。

## 11/24 に見つかったこと（この設計に関わるもの）

- **版の有効期間の外の日**：改正のデータの「前」の版が短い期間しか無いと（長崎県営バスの 11/24〜11/30）、それより前の日はバスが0本になり、「行けるようになる」と誤って出ていました。有効期間の外の日に印を付け、比べる日から外すように直しました。もっと良いのは、その日に有効だった前の版をつなげて使うことです。時刻表のデータが全フィードにそろえば、「前」の側にその日の版を使えるようになります。
- **比べる日が無いとき**：羽後交通（田沢湖地区）は「前」の版が夏の版（〜8/15）で、変更日の前の35日に時刻表のデータがありません。この場合は「くらべられません」と出すようにしました。

## 作った結果（2026-11-24）

- 形：時刻表は版ごと（`data/timetables/{feed}/{uid}.json`、timetable-1）。改正のデータは「日ごとに使う版の uid ＋ 印 ＋ 停留所の対応」（revision-2）で、前の版の時刻表と後の版の時刻表を参照する。変更日の前の日は、その日に有効だった版（新しい版より前に公開され、有効期間にその日が入る版のうち、いちばん新しく公開された版）を使う＝前の版をつなげる。
- 「その日に走るバス」は、端末の計算（`app/js/timetable.js`）が調査の Python（`Feed.services_on`）と同じになることを、米沢（2版）・長崎県営・八戸・根室の 1,043 日分で確かめた（`app/test/timetable.test.js`）。
- 最初の時刻表：手元で、612フィードのうち537版を作った（路線の形は入れない）。gzip で合計 9.4MB、中央 6.3KB、最大 718KB（産交バス。展開すると 6.5MB）。作れなかったのは2フィード（瑞穂町のデマンド交通は stop_times に stop_id が無い、柳川市は arrival_time が無い）。
- バスの一覧：612フィード（使える 541）。使えない 71 のうち 2 はライセンス（掛川市）、69 は今日から120日に有効な時刻表のデータが無いフィード。`catalog.json` は 347KB（gzip 52KB。祝日の一覧と改正の一覧を含むため、見積もりの 15KB より大きい）。
