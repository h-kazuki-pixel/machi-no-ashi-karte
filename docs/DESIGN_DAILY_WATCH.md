# 設計案：全国のフィードを毎日見る仕組み（2026-11-24、まだ作っていません）

## 条件（開発者）

- 毎日1回、全フィードの版の一覧を取る。
- 新しい版の「初めて見た日時」を記録する。
- 便や時刻が変わった版は、改正のデータ（アプリ用の JSON）を作る。
- Mac を開いていなくても動く。

## 結論

- **GitHub Actions の定時実行（schedule）で動かせます。** リポジトリを公開にすれば、無料で動きます。
- **API の利用規約に合う使い方にできます。** 規約には、アクセスの回数の決まりはありません。禁止されているのは「サーバーの機能を妨害する行為」「サービスの運営を妨害するおそれのある行為」（第6条）です。利用ガイドは、時刻表を案内するアプリには「自動で最新のデータを取得してください」と勧めています。毎日のリクエストは数十回、週1回の点検で約600回に抑えます。
- 動かす前に、運営元（AIGID、gtfs-office@aigid.jp）に、毎日の自動取得と User-Agent の連絡先を一言伝えておくのがよいと考えます。送るかどうかは、開発者が決めてください。

## 確かめたこと（11/24）

| 確かめたこと | 結果 |
|---|---|
| 全部の版を1回で取れるか | **取れません。** 仕様では `/files?target_date=all` が「すべての期間で検索」とありますが、実際はフィードごとに最新の1版（612件）しか返りませんでした。`file_rid` も "not_implemented_yet" でした。応答に18.6秒かかり、事業者のメールアドレスも含まれます。この方法は使いません。 |
| フィードの一覧で、新しい版に気づけるか | **気づけます。** `/feeds`（1回のリクエスト）の `last_published_at` は、612フィードすべてで、版の公開日のいちばん新しい日と一致していました（11/23時点）。ただし日付の単位です。 |
| 「最終更新日」の意味 | 利用ガイドでは、`last_updated_at` は過去の版を直したときにも変わります。`last_published_at` と両方を見ます。 |
| 応答の圧縮 | `/files` の応答は、こちらから頼んでいないのに gzip で返ってきました。取得する部品で、圧縮された応答を展開するように直します。 |
| GitHub Actions の定時実行 | 公開リポジトリでは、60日間リポジトリに動きが無いと、定時実行が自動で止まります。混んでいる時間（特に毎時0分）は遅れたり、取りやめになったりすることがあります（公式の説明）。 |
| GitHub Actions の料金 | 公開リポジトリの標準ランナーは無料です。非公開リポジトリは、Free プランで月2,000分までが無料です（公式の説明）。 |

## しくみ

```
毎日 03:17（日本時間）  GitHub Actions（schedule。毎時0分を避ける）
  │
  ├─ 1. フィードの一覧を取る        GET /v2/feeds                         1回
  │     前回の state/feeds.json と比べて、次のフィードを「見直す」に入れる
  │       ・last_published_at か last_updated_at が変わった
  │       ・last_published_at が前回見た日と同じか、それより後（同じ日の2回目の公開を見落とさないため）
  │       ・新しく登録されたフィード
  │
  ├─ 2. 見直すフィードの版を取る    GET /organizations/{o}/feeds/{f}?max_prev=5   1.2秒あけて順番に
  │     state/versions_seen.csv に無い版 → 新しい版として「初めて見た日時」を記録する
  │     前は見えていたのに消えた版 → 「消えた版」として記録する（置き換えに気づくため）
  │
  ├─ 3. 新しい版ごとに、ひとつ前の版と比べる   zip を2つ落とす（作業場所だけに置き、残さない）
  │     03_diff_versions と同じ比べ方で A／B／C を決める
  │     A（便や時刻が変わった）で、ライセンスが加工データの公開を認めている
  │       → 06_build_revision で改正のデータを作る   public/revisions/{feed}/{変更日}.json
  │
  ├─ 4. 結果をコミットする（state/ と public/）
  │     毎日コミットするので、「60日間動きが無い」で定時実行が止まることもない
  │
  └─ 週に1回（日曜）：全612フィードの版を取り直す点検（約13分）
        1〜2 で見落とした版や、置き換えられた版に気づくため
```

### 記録するもの

`state/versions_seen.csv`（1つの版に1行。公開する）：

| 列 | 中身 |
|---|---|
| feed, gtfs_file_uid | どのフィードのどの版か |
| first_seen_at | **この仕組みが初めて見た日時**（実行した時刻。日本時間） |
| published_at, created_at | API の公開日時（参考。置き換えられた版では、最初の公開とは限らない） |
| from_date, to_date, rid（初めて見たときの区別）, declared_kind, license | 版のメタデータ |
| kind | A／B／C／same／比べていない |
| actual_change_date, lead_days_seen | 実際の変更日と、「変更日 − 初めて見た日」 |
| revision_json | 作った改正のデータの場所 |
| gone_at | 一覧から消えたことに気づいた日時 |

- 「初めて見た日時」の精度は、1日1回なので、最大でおよそ1日（＋定時実行の遅れ）です。もっと細かく知りたいときは、1〜2 だけを6時間ごとに動かせます（`/feeds` は1回のリクエストで軽いため）。
- 毎日更新の12フィード（三重交通・熊本）は、毎日新しい版が出ます。毎日 zip を2つずつ落として比べます。zip は1つ330KB〜2MB で、ほとんどが B（期間だけ）になります。

### 1日のリクエストの見積もり

| | ふだんの日 | 週1回の点検 |
|---|---|---|
| フィードの一覧 | 1 | 1 |
| 版の詳しい情報 | 15〜40（毎日更新の12フィード＋その日に公開があったフィード） | 612 |
| zip | 新しい版の数 × 2（30〜80） | 0（新しい版があれば、その分だけ） |
| 合計の時間 | 2〜4分 | 約15分 |

どのリクエストも、1.2秒以上あけて順番に取ります。User-Agent の連絡先は、リポジトリの Secrets に入れた `GTFS_CONTACT` から読みます（ファイルには書きません）。

## 守ること

- zip はリポジトリに入れません。作業場所に置くだけで、実行が終われば消えます。
- 公開するのは、メタデータ（付帯データ。CC BY 4.0）と改正のデータだけにします。改正のデータは、加工したデータの公開を確かめたライセンス（CC BY 4.0、CC0 など）のフィードに限ります。それ以外のフィードは、メタデータの記録だけにします。
- 事業者のメールアドレス（`organization_email`）は、記録しません。
- 同じ実行が重ならないようにします（`concurrency`）。失敗したときは state を書き換えません。翌日の実行が、取りこぼしを拾います。
- 失敗が続いたら、GitHub の通知メールで開発者に届きます。

## 決めてほしいこと

1. **リポジトリを公開にするか。** 公開なら無料で、60日の決まりも毎日のコミットで避けられます。非公開なら月2,000分までが無料で、この仕組みは月100〜150分の見込みです。ただ、非公開リポジトリの定時実行には「有料プランでないと動かない」という報告があり、公式の説明では確かめられていません。非公開で動かすなら、最初に試して確かめます。
2. **改正のデータを、どこから配るか。** 同じリポジトリの GitHub Pages が手軽です。
3. **運営元（AIGID）に、毎日の自動取得を伝えるか。**
4. **「初めて見た日時」の精度。** 1日1回でよいか、6時間ごとにするか。
5. **毎日更新の12フィードの zip を、毎日落とすか。** 落とさない場合は、週に1回だけ比べる形にもできます。

## 作る順番（了承をいただいたら）

1. 取得の部品を直す（gzip の応答を展開する、`max_prev` を絞って取る）。
2. `scripts/07_daily_watch.py` を作る（1〜3 と、週1回の点検）。手元の Mac で、3日分ほど試します。
3. `.github/workflows/daily-watch.yml` を作る（schedule と、手で動かす workflow_dispatch）。まず手で1回動かし、問題がなければ定時実行に切り替えます。
4. `public/revisions/` の目次（どのフィードに、どの日の改正のデータがあるか）を作り、アプリが読みに行けるようにする。
